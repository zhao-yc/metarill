# 管理准备包的基础物理图一致性

日期：2026-10-30；起点 `0b251fe69a1044f22286ca4b4e4626e6fd7f4584`，对应 C05/C49。本批修改管理装配源头，不修改元数据、普通生成模板、原前端或现有工程。

## 实际复现

工厂的管理物理图来自固定嵌入资产，普通完整包却读取指定源码根的 `files.json`、`security.json`。原准备器先创建普通完整包，再用嵌入资产重建管理目录，没有核对两套基础定义是否一致。

在本轮独占临时源码快照中，分别改变文件基础字段长度、项目基础字段 `yz_project.name` 长度、唯一索引定义。三份输入均能正常生成普通完整包，但旧管理准备器也全部成功，没有拒绝与其冻结管理图矛盾的基础版本。新反例实际得到3项失败，均为预期异常没有抛出。没有连接数据库或修改已提交元数据。

## 修复

普通完整包完成后，读取实际装入候选包的两份基础元数据，由工厂仅向已签发模块提供固定基础副本，先核对完整表标识集合，再通过现有 `MetadataCatalogComposition.MergePhysical` 合成。字段类型/长度/默认值、精度、索引唯一性、字段顺序及方向等继续按公共比较器校验；不另写一套宽松结构规则。

只合成相交表仍不充分：第一轮修复的9项通过后，新增整表增加/遗漏反例实际得到2失败、6通过。合成器允许合法新增表，因此本批追加完整表集合校验，既不接受额外表，也不放过基础表遗漏。原失败记录保留。

校验发生在管理再生成及最终发布前；错配明确要求先同步基础元数据、重新派生管理模块。清理仅沿原有本轮stage所有权规则。验证对象是已复制的实际包文件，避免只检查原始路径再读到另一版基础定义。

说明文案、JSON排列和项目绑定不参与物理比较。正例同时修改文案和字段数组排列，准备包仍应成功；不能用整个原始JSON字节摘要替代物理兼容判断。
