# V323 混合关系传播结构核验复用

V322 的 8 行子页导入显示，同一批中的混合传播反复执行依赖表的 `LIMIT 0` 和结构检查。当前运行时改为同一个会话事务内，按已编译计划对象复用已完整验证的结构。首次仍取得元数据锁并检查 InnoDB、依赖列、可空性、计算列和主键。缓存命中继续读取实际库名和会话报文限制。每行的权限、父记录及关系锁、缓存写入和读回继续执行，独立回填仍做完整预检。

依据是 MySQL 在显式事务结束前保留已使用表的元数据锁。Server-200 实际用独占空表执行 `SELECT id … LIMIT 0`，另一连接尝试 ALTER 返回 1205，原事务回滚后同一 ALTER 成功。独立 SSH 核验该表已清理。[MySQL 元数据锁说明](https://dev.mysql.com/doc/refman/8.4/en/metadata-locking.html#metadata-lock-release)

另一个实际 MySQL 独占空表由当前 C# 运行时执行结构核验。观察器验证首次执行 4 条命令，同一事务复用只执行 1 条，下一事务重新执行 4 条。探针核对两个提交和两次 `LIMIT 0`，另一连接及独立 SSH 均确认表已回收。离线用例额外覆盖嵌套事务、不同计划、连接库名不符和后续事务引擎不符。数据层共 1,572 项通过、29 项条件跳过，混合传播及维护的生成回归通过 11 项。

旧混合关系 HTTP 夹具的两项实库用例停在文件结构准备阶段。既有 `metarill_business_test.yz_file_library` 缺少当前文件元数据中的 `upload_expires_at`。首轮在检查前已创建两组共十张独占空表，原清理也因缺列中断。已只读复核十表零行、无触发器或外键、四个预留文件 ID 和引用均未写入，然后仅回收本轮十表并用新 SSH 核零。现将文件结构检查移到样本登记与创建前，真实回归确认缺列时提前拦截。共享表保持原样。

本轮 4→1 的结果只覆盖单表结构核验。完整子页的优化后 SQL、混合关系业务实库及正式性能计时仍待验收。
