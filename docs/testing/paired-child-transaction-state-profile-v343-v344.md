# V343／V344 同父子页事务状态诊断

Server-200 使用 V342 同一组 Java 与 C# 应用镜像、相同种子、关系索引和普通账号，关闭应用 SQL 观察。每轮 32 次预热及 1,200 次诊断请求均成功，两端每轮各 4,928 行逐值一致，原种子保持。新连接独立核验两轮的双库、账号、容器、网络、源凭据和数据副本均已清理，分别复算 59 份应用证据。

V343（轮次 `1117fdeb840f47b18cfdba87dff45632`）每 75 毫秒联接读取 MySQL 连接与 InnoDB 事务状态，收得 857 个样本。六组中有三组在连接有活动时始终没有可配对的 InnoDB 状态。第二组可配对，Java 和 C# 的行锁等待占用估算均约 322–323 毫秒／请求。缺配组的零等待不能作性能证据。MySQL 文档说明连接视图与 InnoDB 事务视图的快照可能不一致。 [MySQL 状态视图的一致性](https://dev.mysql.com/doc/refman/8.4/en/innodb-information-schema-internal-data.html)

V344（轮次 `7779924baf90415287d0ba6fb18475a1`）分开读取连接与事务，并独立统计原父记录排他锁查询是否仍在执行。采样器只向本机输出本轮用户和双库的分类计数，无 SQL 正文或线程号。827 个样本覆盖全部六个四并发时段，采样查询的逐组 p95 最高 3.9 毫秒。InnoDB 状态在五组仍无法稳定匹配，因此以下以连接视图直接识别的父锁查询为对照。

| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 226.2 | 299.7 | +73.5 | 358.4 | 443.7 | +85.3 |
| 2 | 260.9 | 292.7 | +31.8 | 393.2 | 432.8 | +39.5 |
| 3 | 250.4 | 274.7 | +24.3 | 380.5 | 412.6 | +32.1 |

单位为毫秒／请求。父锁查询占用以采样点的并发查询数乘覆盖时间后除以成功请求数，包含查询自身执行与排队，不能直接当作单笔锁等待或持锁时间。三组 C# 的占用增量与 HTTP 差同向，支持继续缩短父锁取得到事务提交的串行路径。当前样本不足以把差距进一步归到提交或锁内 SQL。两轮为诊断，首版正式性能判定继续沿用 [V342](paired-child-scalar-cache-timing-v342.md)。
