# V935 同合同明细导入性能差距复算

2026-11-10。以 [V929 父快照复用对照](same-parent-snapshot-reuse-v929.md) 的固定数据为输入。重新从 12 个窗口的 1,200 条 HTTP 原始记录计算吞吐和 p95，从服务端原始提交事件计算 COMMIT、waiting for handler commit 和已采到的前台 binlog 同步均值。三份输入逐份记录 SHA-256，复算与原报告一致。未新增负载或更改 MySQL 设置。

按原阈值，四并发每个窗口执行 100 批。要达到 Java 吞吐的 95%，C# 窗口耗时上限为 100 除以 Java 吞吐的 95%。HTTP p95 上限为同轮 Java 的 1.10 倍。下表列出 C# 实测超过上限的幅度，服务端差值均为 C# 减 Java。

| 四并发轮次 | 每 100 批需缩短（秒） | HTTP p95 超限（毫秒） | 父锁返回至提交前均值差（毫秒） | COMMIT 均值差（毫秒） | 前台 binlog 同步均值差（毫秒） | 扣除前台 binlog 同步后的提交差（毫秒） |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1.08 | 27.30 | 3.49 | 12.68 | 0.91 | 11.77 |
| 2 | 1.33 | 20.18 | 6.37 | 12.14 | 2.82 | 9.32 |
| 3 | 1.49 | 31.61 | 8.12 | 11.93 | -0.74 | 12.67 |

窗口耗时和服务端分段属于不同统计边界。扣除项仅是差额比较，未归属的 9.32 至 12.67 毫秒可能同时包含多种提交开销，不能直接计作 redo 时间。第二轮先跑 C#，第一及第三轮先跑 Java，三轮差额方向一致。结合此前 [binlog 压缩对照](current-binlog-compression-v920-v924.md) 和 [redo 写入线程对照](current-redo-writer-control-v926.md)，后续重点是区分提交等待的来源，并在原持久化和逐行核验合同下复测。

发布继续以 [V912 当前候选正式矩阵](current-exact-mysql-performance-v912.md) 判定。同合同四并发仍阻断首版性能验收。
