# V689 固定候选 binlog 同步与 redo 等待

2026-11-09。使用 `c2eddf71` 和原固定双端镜像，在 Server-200 新的独占 MySQL 8.4.11 保持 `sync_binlog=1`、`innodb_flush_log_at_trx_commit=1`。完成 230 个原 HTTP 诊断请求。普通角色、相同索引、物理样本与回收均独立核对。条件／互斥采集项实际启用 32 个。

178 笔服务端提交都捕获到同一提交线程的 binlog 文件同步。按线程及嵌套事件归属前台等待，每类等待按自身时钟求持续时间，避免跨计时器对齐起点过滤掉有效事件。已采集项中没有同线程条件等待。独占实例计数显示 178 个写入窗口均有 redo 等待计数增量，52 个只读窗口均为零。

下表各列为 Java／C#。每端使用相应操作的最慢 HTTP 样本。前四列耗时单位为毫秒，最后一列为计数。

| 操作 | HTTP | 服务端 COMMIT | 同线程 binlog 同步 | 实例 redo 文件同步累计增量 | 实例 redo 等待增量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 明细逐次修复 | 292.2／333.9 | 143.0／222.8 | 91.2／66.9 | 130／167 | 2／2 |
| 删除副本 | 188.3／111.8 | 125.1／84.0 | 89.1／59.8 | 56／104 | 1／1 |
| 复制接口 | 177.4／132.1 | 117.7／79.4 | 75.3／31.7 | 75／64 | 2／1 |
| 合同逐次修复 | 350.9／228.0 | 79.9／113.3 | 33.6／41.6 | 91／91 | 1／2 |

明细最慢 C# 样本约 333.9 毫秒。服务端提交约 222.8 毫秒，其中同线程 binlog 同步约 66.9 毫秒。同窗口实例 redo 文件同步累计增加 167 毫秒，可能覆盖前台请求期间的多个后台活动，与 binlog 时间分列。MySQL 8.4.11 的 redo 刷盘等待走日志线程的事件路径，按等待和循环计数统计，文件同步累计以毫秒记录。见 [MySQL 等待归属](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-wait-tables.html)、[MySQL 8.4.11 redo 刷盘源码](https://github.com/mysql/mysql-server/blob/mysql-8.4.11/storage/innobase/log/log0write.cc#L789-L842) 和 [同步累计单位](https://github.com/mysql/mysql-server/blob/mysql-8.4.11/storage/innobase/log/log0write.cc#L2142-L2167)。

本轮说明提交长尾同时涉及 binlog 同线程同步与 redo 活动，未对全部服务端提交耗时逐毫秒归因。正式性能结果单列，明细逐次修复仍以 [V688](fixed-write-formal-recheck-v687-v688.md) 阻断。新 SSH 已核清双库、账号、15 个容器位置、独占 MySQL、网络、源凭据与合成数据。
