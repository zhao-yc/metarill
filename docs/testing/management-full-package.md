# 显式完整管理应用打包

日期：2026-10-30；起点 `41f1015d07b7161dcf84b9a8d29bc385ba2af69b`，对应C05/C51。此处区分打包实现、宿主回归与正式验收，不代表MySQL首版已完成。

## 打包入口与模式

新增 `ApplicationPackager.CreateManagement`，必须明确指定原业务目录中已发布的后台ID。CLI提供：

```text
metarill package --metadata 原业务.json --output 新空目录 --namespace 根命名空间 --source-root Metarill源码根 --management-admin-type 包内后台ID
```

输出模式为 `FullManagementApplication`，包含原管理页、权限工作台/组件、三份安全partial、当前生产宿主及Web/Agent/MCP完整源码闭包。普通 `FullApplication` 和 `BackendOnly` 参数行为保持，管理模式不能与 `--backend-only` 同用，也不能通过给普通Create传枚举值省略后台选择。

原业务先沿普通完整包脱敏，再由固定工厂重签发管理目录，沿C49核对实际基础物理图、C50核对可恢复业务来源。非空工程、未知后台、保留表冒充普通业务均拒绝；完整包发布失败保留本轮所有的候选及诊断，不留下半发布输出。

## 能力判定与来源

实际编译红灯确认，绑定了真实管理Service的模型仍被一条旧的“Runtime A待验收”编译提示阻断。现在仅当工厂完整冻结快照实际选择受守卫Service模板时，视作协调器已经接线；普通模型、隐藏/改坏角色字段和未绑定目录的原门禁继续。代码接通不等于正式身份、数据库和工作台矩阵已验收。

声明的四项RequiredBackendAdapters是固定模块的依赖，不等于缺少实现；项目候选、角色工作台、初始化和安全写协调均由当前实际模板/生产注册提供。真正的其他BackendGaps仍使完整包失败，不按客户端标志放行。

新包使用 `.metarill-package.json` 及固定 `managementModule` 绑定，来源声明从准备状态中独立为 `.metarill-management-source.json`，只登记实际读取的五份元数据。C50仍能从旧准备声明重建，新旧来源声明同时存在明确拒绝。完整源码/前端归属由外层包清单负责，来源声明不是发布、更新或数据库授权。

## 当前使用边界

本批尚未接完整管理工程的受管更新。现有更新器明确拒绝该新模式，CLI和生成README也说明这一点；不能把它冒充普通Full接入原更新流程。该边界是尚未完成的C05功能，后续必须继续接线。

正式初始化中有效Agent刷新授权的处理决定仍待确认，当前保持原明确拒绝。新包不自动连接数据库、安装结构或初始化账号；此批未消费任何待确认实库范围，也没有容器或生产部署。
