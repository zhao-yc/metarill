# V879 同父明细导入日志量对照

2026-11-10。固定产品 `ffcd80d36cc90283e7cb065ba78f65d1874d4c25`。使用 V876 的 Java、C#、Redis 镜像、原八行工作簿、普通角色、共同索引和资源限制。在 Server-200 同一存储设备的独占 MySQL 8.4.11 上运行，`sync_binlog` 和 `innodb_flush_log_at_trx_commit` 均为 1。

12 个计时窗口逐个核对。1,200 个计时请求、32 个预热均完成，原回包指纹一致，两端各 4,928 条新增明细通过物理读回。每个窗口均为 100 笔事务，两端各有 100 次 COMMIT 和 100 次 binlog 事务缓存使用。每笔均八条明细 INSERT，600 笔 C# 事务各有八次缓存来源读及八条 UPDATE，Java 在 INSERT 中写缓存。

日志状态只在请求计时窗口前后读取。12 个窗口均在同一 binlog 文件内取位置差。redo 以 MySQL 实例的实际日志文件写入字节计，另记录 LSN 增量、redo 同步和写入次数。未读取二进制日志正文。 [MySQL binlog 状态](https://dev.mysql.com/doc/refman/8.4/en/show-binary-log-status.html) · [MySQL 状态变量](https://dev.mysql.com/doc/refman/8.4/en/server-status-variables.html)

| 1 | 275,200／671,700 | 708,608／1,358,336 | 306／317 | 13.79 ms | 1.1741 | 0.8516 |

六个配对轮次的 binlog 增量均为 2.44 倍，redo 实际写入为 1.92–2.11 倍。四并发三轮中，写入量差和平均 COMMIT 时差方向一致，但各轮 COMMIT 时差不随固定的 binlog 差等幅变化。redo 和同步是实例窗口统计，不能分配到某条缓存 UPDATE，也无法单独确定磁盘同步、提交分组各自的贡献。

后续用同一产品的既有部署证明做对照，核验后七行单次写入是否减少日志和提交耗时。已配置路径的结果单独记录，默认权限的正式门槛继续以 [V875](current-mysql-performance-v875.md) 为准。本轮隔离诊断四并发三轮触线，未改变发布状态。
