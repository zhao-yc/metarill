# V659 当前候选降序索引反查与保存

2026-11-08。使用当前 Linux 候选 `31cf5321`，在 Server-200 的独占 MySQL 8.4.11 和 Redis 上启动 Production 分库平台，以真实 Web 管理员账号访问正式 HTTP 接口。平台库和业务库各有一张同名合成表，平台表只有升序索引，业务表有 `rank_no DESC, group_no ASC` 复合索引。逐份核对 311 个固定文件。

| 检查 | 实测结果 |
| --- | --- |
| 反查与审批 | 业务项目反查草案及审核均保持列次序和 `DESC/ASC`。未登录审核被拒绝，草案及审核均为零配置写入。切到平台项目提交同一审核凭证被拒绝，回业务项目仍为 `prepared`。 |
| 审核后结构变化 | 只改变业务源表首列方向后，确认旧审核失败，回执为 `unconfirmed`，独立 SQL 确认零配置写入。恢复方向后重新审核并确认。 |
| 保存与物理反查 | 仅业务项目新增一张表、四列、一个索引和两个索引成员，零页面。独立连接从平台配置表读回 `DESC/ASC`，从业务库 `information_schema` 读回 `D/A`。实际两张源表 DDL 和原有记录保持。回执为 `saved`，重复确认被拒绝。 |
| 正向差异保护 | 保存后预览零差异。再次只改变业务库首列方向，同名索引因物理结构不同被拒绝，指纹改变，平台未重建索引且无 DDL 审计。夹具恢复后再次预览为零。 |
| 会话和回收 | 原会话注销后反查被拒绝。独立 SSH 核验本轮容器、网络、数据库、账号、所有权与临时数据已回收。 |

测试夹具的 DDL 仅用于独占合成源表。该记录覆盖分库同名的固定双列降序样本与正式 HTTP，浏览器索引编辑、其他索引特征及其他数据库按原矩阵分别跟踪。
