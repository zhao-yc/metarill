# V559 反查导入的物理名称与项目名称冲突

2026-11-08。使用修复前 `5159c45d` 和本次补丁分别严格发布 Production 宿主。在 Server-200 的 MySQL `lower_case_table_names=0` 上，平台与业务项目指向同一独占物理库。样本包含两张只差大小写的表，分别具有不同列、索引成员和一条已知数据。

| 验证 | 结果 |
| --- | --- |
| 修复前真实对照 | 原目录区分两个精确物理名。两个名字分别反查，得到各自的列；无实际表的大小写变体被拒绝。登记第一张后，旧审核仍对同项目第二张签发计划，保存时按配置唯一规则拒绝，状态为 unconfirmed。 |
| 修复后真实对照 | 同项目的名称比较与生成和结构同步的唯一性规则一致，第二张表在审核阶段直接拒绝。两个真实物理名依然可分别反查，在共享物理库的不同项目分别登记成功。独立 SQL 核对各一份归属、三列、一个索引、零页面，源 DDL 和业务行逐项匹配。 |
| 连接前校验 | 旧正则的行尾匹配放过末尾 LF。新增回归在旧版本分别进入 MySQL 连接和 CLI HTTP 传输后失败。修复后元数据、服务和 CLI 共用整串校验，两个入口均在发请求前拒绝。数据层 1,594 项通过、32 条件跳过；元数据及 CLI 577 项通过、41 条件跳过。 |
| 范围与回收 | 两轮准备中带 LF 的样本未建成，第二轮确认 MySQL 错误 1103。正式对照使用两张有效表；真实 HTTP 仍校验带 LF 的输入，是否在连接前拦截以本机回归为准。四轮的独占双库、账号、所有权、Redis、配置与转发均核清。 |

本轮覆盖实际大小写敏感的 MySQL。其余 MySQL 名称模式、触发器可见性及浏览器仍按 [实施进度表](../project-progress.md) 跟踪。
