# 角色工作台身份后台恢复

这是step A的第一个小切片，仅纠正角色工作台realm与revision；不改变原URL、JSON、组件、交互或表结构，不接角色复选控件，也不关闭唯一角色Gap。

## 已恢复的范围

- roles、snapshot与save以真实身份PrincipalAdminTypeId定位角色，不再把Actor.ProjectId开发工作区或兼容yz_role.yz_project_id列作为角色归属。
- 目录先读取PrincipalProjectId，再筛该真实后台的菜单与页面；按钮必须属于该后台页面。同项目其他后台也不能混进目录或保存白名单。
- 保存继续使用原事务及已有项目锁，但锁与新授权行的项目归属改用身份项目；用户切到业务工作区不会把平台角色授权写进业务项目。
- revision由角色ID、后台、超级标志、范围标志、同后台目录与授权源行共同计算。角色语义、页面、菜单、按钮或授权变化均使旧草稿冲突。摘要不对外输出元数据原文、SQL或连接信息。

工作台原请求仍是GET roles、POST snapshot {roleId}、POST save {roleId,revision,grants}，长ID和RESOURCE响应结构保持不变。

## 本小片的暂态门禁与最终决定

本小片保留当前RequireAdministrator入口及超级角色资源授权只读逻辑，避免将归属修复与开放操作混为一次修改。此门禁是迁移暂态，不是新增的最终产品规则。

用户已确认：最终沿用原V8页面编辑权限和真实目标后台归属，不额外增加超级身份门槛。后续固定控件/权限闭环必须据原角色页、账号页新增/修改/查询权限恢复普通账号操作，不能继续一概以platformsuper挡住；不能擅自禁止合法的同后台超级角色绑定或isSuper修改。业务后台super仍不能取得平台全局权限或Agent审批权，这是身份realm边界。跨后台角色关联、直接搬角色后台及有引用删角色仍按原规则拒绝。
