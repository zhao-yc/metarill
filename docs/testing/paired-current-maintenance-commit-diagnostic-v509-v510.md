# V509／V510 合同逐次修复提交长尾诊断

2026-11-07 在 Server-200 沿用 V507 的 C# 产品 `389a9c68`、镜像 `d7ed8a6ce83f`、Java `ecd22231140f`、Redis `ff02b58f971e` 及原逐次修复预算。两轮分别从空库显式初始化，核对每端 10,752 行同摘要种子、共同索引、原表单普通身份和原容器限额。仅对 C# 独占宿主启用镜像中的既有命令与事务观察器，两轮分别执行 8 次预检、64 次预热、144 次正式场景请求。每次回放重新置旧 132 个缓存值，全部逐值读回，原数据前后保持。

V509 的 HTTP 与物理结果均通过，观察器因批写超过 256 个参数摘要而将快照标为不完整，未通过诊断验收。V510 的独占收集器单列参数证明截断，继续严格核对请求标签、摘要、命令与事务的连续序号、时间戳、事务提交配对和已终结索引。7 项离线契约通过。实测匹配 108 个 C# 维护请求，其中 104 个为修复回放，106 个请求存在参数摘要截断。截断只允许用于本次时间审阅，参数完整性仍以原观察器状态为准。收回材料仅包含脱敏阶段耗时、计数和验证回执。

V510 的合同和明细各有 36 个正式 C# 诊断样本。合同提交调用中位数为 61.7 ms，明细为 77.3 ms。最慢的合同请求调用端为 534.0 ms，宿主为 520.3 ms，MVC 动作为 511.7 ms。驱动与事务观测区间共 508.4 ms，其中 `CommitAsync` 为 **469.4 ms**，17 次加锁读合计 26.0 ms，两次更新合计 4.9 ms。

长尾已定位到客户端事务提交调用边界。此时间覆盖服务端处理、往返及调用方恢复，不能单独归因于刷盘、锁或调度。读命令时间止于 `ExecuteReader` 返回。Server-200 独立只读预检确认当时共享实例启用二进制日志，`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`、`binlog_group_commit_sync_delay=0`，`performance_schema=OFF`，该实例当前无法提供逐语句服务器事件。下一步在独占 MySQL 环境保持相同持久化配置，采集服务端 COMMIT 与客户端边界进行对照，之后用原未开采集的逐次修复负载复验。
