# 角色管理权限规则（已确认）

用户已明确选择：沿用原V8，按账号/角色页面的编辑权限和目标后台归属判断，不增加超级身份门槛。此前提出的额外收紧方案不采用。页面、复选控件、全选及原请求协议保持。

原V8静态调用链按页面新增/修改权限授权；账号写守卫验证全部角色属于合并后的目标后台，未另设“仅超级角色才能绑定超级角色”的检查。已核对资源模式拦截器、管理员Controller、页面写执行器和写守卫；未实际通过普通账号HTTP授予超级角色，不能把静态证据写成已复现越权。

| 操作 | 最终实施规则 |
| --- | --- |
| 账号新增/修改与角色分配 | 核对应页操作权限、真实目标记录范围和后台归属；不因涉及超级角色增加身份门槛 |
| 角色超级标志修改 | 沿用角色页修改权限和同真实后台规则 |
| 角色候选 | 沿用原来源页查询/新增/修改权限，服务端核目标后台；客户端提示不授予权限 |
| 直接将角色搬到其它后台 | 继续按原守卫拒绝，独立迁移不包含在标准保存中 |
| 删除有授权或账号引用的角色 | 继续拒绝 |
| 账号省略角色字段 | 保留旧角色并参与合并后后台归属校验 |
| 空数组或JSON null | 沿用原清空集合语义；编码字符串“null”不当作有效数组 |
| 业务后台超级角色跨到平台或Agent控制面 | 不因角色控件接通获得平台全局权限 |

当前C#平台配置页的普通账号门禁只是尚未恢复完整角色链的迁移状态，不能作为最终额外超级门槛。后续固定安全表范围、角色工作台和手写YzRole钩子须同步按上述规则恢复；不能只放开Controller却丢掉同后台和保存校验。此确认不自动给任何账号新增页面权限。

事务与并发保护继续实施：身份后台和开发工作区分开，工作台目录按真实后台定位；项目/后台稳定锁序，等待锁后以当前读重新验证会话、操作者、授权与目录，旧草稿冲突整笔回滚。角色能力缺口在完整控件、保存和实库验收前仍不关闭。
