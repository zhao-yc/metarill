# 非冗余多选的固定派生名称

## 行为与范围

来源R0多选通过物理target_ids关联R0目标，目标name再通过company_id联接公司name。显式target_names与自动名称都沿原JSON数组合同，只存ID；改公司名称后即时读取当前名称，不重写来源名称缓存。原MultiSelectPage、type=2目标页、页面、样式与交互保持。

原实现同时在生成证明、底层多值聚合及Excel名称反查要求物理名称。仅解除前端或生成拒绝会产生对IsIgnore属性的无效SQL。本批将目标单值名称编译为固定计划：

- SQL名称元素筛选使用同一受限目标联接，在COUNT／分页之前执行；不会把来源JOIN成多行。
- 目标名称联接在独立固定别名域中，保持项目和软删范围；来源数组顺序及不可见上游的null位置保留。
- 页面实际读取合并目标ID并按200项分批，同事务写回显使用目标与上游的当前锁读；请求不解释元数据或提供表／列／表达式。
- 原Excel名称数组在来源import事务中按同一目标项目、真实父、页面常量条件逐项唯一反查；采用当前读，缺失或重名撤销整批，不能借用create／update／目标list权限。
- 隐藏多选继续参与默认值、复制和依赖变更的最终校验；未发布名称、凭据、数组、坏路径、循环、隐式字符串联接键和未接线存储组合仍在stage写入前拒绝。

仅开放R0来源MultiSelectPage、普通R0目标、非凭据单值字符串联接名称与物理目标范围。全局目标、逻辑父范围、精确数据权限、非字符串／嵌套多值／级联名称、R1物理派生缓存及其它控件继续保留门禁。它不代表所有复杂联接、混合传播或维护回填已经完成。

## MySQL TEXT默认常量修复

隐藏默认ID数组的真实建表发现原LONGTEXT DEFAULT '…'无法执行；补括号后又发现MySQL 8.4的COLUMN_DEFAULT以带字符集和转义边界的文本表示该常量，原EXTRA判断将DEFAULT_GENERATED误判为生成列。现仅对已证明的TEXT／LONGTEXT字符串常量生成表达式括号，并识别该固定反查形态；其它函数表达式、未知转义、未知EXTRA与真实生成列保持保护，不从请求接受SQL。

该语法要求MySQL 8.0.13及以后，Server-200验收实例为8.4；此处语法下限不代表平台已验收全部MySQL版本；规则见[MySQL官方默认值说明](https://dev.mysql.com/doc/refman/8.4/en/data-type-defaults.html)。字符串常量、VARCHAR原合同及显式预览→执行→核验→审计流程保持。更新只修正适配层，不启动自动同步或回填。

## 更新与后续

已有本固定模型应用先同步同版Data与生成器，再正规生成受影响后端和原页面。新增MySqlNonRedundantReadPlan.MultiNames.cs只登记精确运行时更新路径，原三动作预览／依赖检查／应用、AppID／私有配置和手写partial保护不变；未知相邻分部文件仍拒绝。已有正确逻辑名称模型不新增名称物理列或历史回填；元数据变更仍先预览结构，已有TEXT默认值按实际预览核对，不自动批改业务库。

本批尚未增加正式身份／专属空库、原浏览器、跨端和同条件性能结果；整个复杂关系与MySQL首版仍继续。原浏览器专用空间重建问题、非空路径Excel策略和TinyCloud配置仍沿既有待办，不合main、不部署生产，新提交CI另核。
