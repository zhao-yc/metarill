# 普通多值关系引用全局R1名称缓存

2026-10-31，B107；产品起点ba7ced6。补齐普通R0/R1的原type=2多选和数据库复选到已证明全局R1名称缓存的本地链路。尚未完成本组合的真实MySQL保存、传播、维护、锁及文件回滚，不计作复杂关系或MySQL首版全部完成。

## 范围与边界

示例：共享字典 `global_target.name` → 无项目列全局R1物理List中间缓存 `global_source.global_target_name` → 普通项目的多选/复选ID数组和名称数组。

- 来源保持真实项目列和物理JSON文本ID数组。R0读取中间表已有物理名称缓存，仍按原数组顺序保留缺失目标的null位置；名称筛选在分页前处理，不把根行联接成多份。R1名称数组进入原物理传播和维护计划，原多选200/复选5000预算保持。
- 全局名称必须是原非凭据物理字符串，或B105同一套递归证明得到的全局R1字符串副本。每层仍要求当前目录明确发布、没有项目列的全局物理List来源、真实主键/后台页、精确联接与副本路径，以及最终非凭据物理字符串；16层上限及循环门槛未改。
- 新能力没有开放全局R0实时派生目标、全局来源的多值生产链、跨表级联缓存名称、数组作标量或任意Join字段。原 `IsScalar` 物理API未改，目标页条件继续只许原物理标量。来源、普通目标及父范围不因global而省略。
- 原数组缓存由物理传播队列唯一维护；中间全局标量副本由混合队列维护。现有项目协调器会将中间修改事件交回同一物理/混合队列，不新增另一套消费者刷新规则。静态闭包不等于真实改名已传播。

## 原复选名称合同

旧空配置、目标字面值、四段及省略JSON名称仍默认 `name`。新JSON可明确声明全局字符串名称，例如：

```json
{"tableId":"1","table":"global_source","pageId":"10","nameField":"global_target_name","whereSql":"status=1"}
```

解析器只承认名称标识符并拒绝凭据；真正可读、可写和可维护资格由全局目标和生成用途证明决定。非默认名称当前只向已证明全局目标开放，普通项目复选继续保留缺口；页级名称不能悄悄替换根定义。未配置排序时按声明名称升序再加原ID稳定排序。既有显式排序不改。

名称同时用于候选投影、显式/自动辅助列、R0投影及R1物理缓存。新完整包验证type=2返回的真实缓存属性，而复选候选仍保留原 `id/name/value/text` 合同。账号/角色等受保护复选不进入这条通用解析接线。原页面、样式、组件及模板均未修改。

## 采用、升级与回退

1. 更新同版Core、Data、生成器及完整应用运行时；不能只替换生成器或仅改JSON。未采用新名称定义的项目无需DDL，原name和四段合同保持。
2. 在元数据中明确真实全局表、目标页及名称。缓存链应已经完整声明为物理List生产链；普通来源继续保留项目及原物理ID数组。多选目标保持type=2及名称可读投影；复选自己的原候选条件和权限继续使用。
3. 明确采用R1新名称时，按预览差异/SQL→执行→核验同步所需数组缓存列；自动名称仍由元数据/生成链推导，不能手补实体或用启动CodeFirst改表。R0不增加名称副本存储。
4. 正规再生成和同步运行时，保护手写partial；通过原维护入口回填上游和R1下游。必须实库核验原候选/已选、保存/导入、改名/删除、重复回填、预算和晚期失败整笔回滚，再宣布该组合正式支持。
5. 回退需配套还原Core/Data/生成产物及原配置，不能把新JSON名称留给旧固定name运行时；不自动删列、删数据或重映射ID。
