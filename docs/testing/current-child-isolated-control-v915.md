# V915 同合同明细导入的隔离对照

2026-11-10。基准产品 `ffcd80d3` 使用 V896 的固定 C# 镜像，当前产品 `68af5319` 使用 V898 的固定发行包派生镜像。两个试验在 Server-200 顺序执行，各使用独占的 MySQL 8.4.11 实例，保持同一存储设备、Java 与 Redis 镜像、种子、普通账号授权、共同索引、八行 XLSX、资源限额及默认排他父锁。逐语句应用观察器关闭，MySQL 仅保留分段诊断与计时边界的持久化统计。两轮均核验每次提交持久化、ROW／FULL 及组提交配置。

两组各完成 1,200 笔正式请求、32 笔预热及 12 个计时窗口。各组两端分别新增 4,928 条明细，逐值核对一致。独立复算报告的阈值与 [V899 正式同条件性能](current-exact-child-performance-v898-v899.md) 一致，单轮 p95 比值大于 1.10 或吞吐比值小于 0.95 即触线，同档三轮两次触线即判为稳定退化。

两组的四并发各窗口均记录 800 次明细 INSERT。C# 另有 800 次缓存来源读和 800 次缓存 UPDATE，Java 在 INSERT 中写入缓存。每百笔 binlog 增量分别为 671,700 与 275,200 字节，约 2.44 倍。基准组四并发 redo 的三轮中位数为 C# 1,372,672、Java 710,656 字节，候选组为 C# 1,419,264、Java 709,632 字节。

两份 C# 载荷均复现四并发瓶颈，候选相对 Java 的四并发吞吐区间与基准重叠。两次运行顺序固定，单并发触线差异和 p95 差异无法仅归因到候选版本。缓存写入、提交与父锁调用同时存在差异。此前只减少排他锁内写入仍未达标，已配置共享锁则通过专项，见 [V881 排他锁单次写入](current-child-exclusive-inline-v881.md) 与 [V880 共享追加对照](current-child-shared-log-volume-v880.md)。后续优化仍须保留默认配置下的父范围校验、缓存传播及整批回滚，再按正式矩阵复验。

各组独占双库、账号、16 个应用容器位置、网络、独占 MySQL、所有权记录、源凭据、数据目录及暂存根，均由独立 SSH 核零。诊断的 2,400 个正式请求单独记录，首版发布仍按 [V912 正式九类性能矩阵](current-exact-mysql-performance-v912.md) 判定，同合同导入门槛继续阻断签收。
