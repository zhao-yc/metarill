# time 逻辑类型与原时间控件

日期：2026-10-29；起始基线0405518，进度编号C36。仅修改C#合同、数据库适配与生成器；原uni-app页面、样式和交互保持。

## 原问题与已确认规则

0405518的正式CLI对带time逻辑列的模型报“未知逻辑类型：time”，且未写出目录。元数据接受time不代表生成链路已经支持。

原Java的LocalTime合同使用Fastjson2 2.0.20。隔离JDK21探针重现：时分、时分秒、1至3位小数和一个完整无偏移日期时间可成功，六位小数却失败；日期文本及部分无效格式可能得到null。用户已确认修复微秒输入及无效文本静默清空，界面不变。探针不是旧HTTP、JDBC或实库验收；原Java的物理原生TIME又会落到String，不能把两者混为一类。

## 两种字段合同

| 元数据用途 | C#存储属性 | 请求及响应 |
| --- | --- | --- |
| logicalType=time且ControlKind=time | TimeSpan?；字段级ClockTimeJsonConverter | 日内00:00至23:59:59及小数；原picker仍提交HH:mm；响应固定HH:mm:ss并按需保留小数 |
| 其他logicalType=time，包括结构反查后的普通字段 | TimeSpan?；字段级SqlTimeJsonConverter | 带可选负号的总小时，不把30小时改成.NET的1.06:00:00 |

日内输入支持HH:mm、HH:mm:ss及1至9位小数；保留合法完整无偏移日期时间提取时刻。数字、布尔、复合JSON、非法日期、偏移、负数及跨日明确报错。原生TIME接受带符号总小时及小数；具体取值范围由IDatabaseProvider承担。MySQL适配器明确验证±838:59:59.000000（端点不能再附非零小数，[MySQL 8.4官方范围](https://dev.mysql.com/doc/refman/8.4/en/time.html)），Service没有数据库品牌判断。其他数据库尚未验收，不能据此宣布支持。

省略字段保持Optional未提交；明确null或空字符串才清空。无效非空文本不能写成null。转换器只用于这些生成字段及Service局部选项，全局TimeSpan配置保持原合同。MCP/Agent请求schema按字段转换器提供对应文本形状，不把原HH:mm或总小时误标为RFC3339 time；字段schema不替代日历有效性或数据库范围校验。生成Service再次检查手写钩子产生的时刻和适配器范围。普通与非冗余筛选、导入、导出、基础设施行存储和固定条件均接入相应合同；集合筛选仍是IN，不变成日期范围。

## 精度与默认值

解析不经过浮点数。输入最多9位，TimeSpan实际承接100ns，低于一tick的末两位不进入该类型；MySQL物理TIME最多6位。不能宣称纳秒无损或Java/JDBC、SQL mode、不同字段精度的截断/舍入完全等价，须通过独立实库专项核对。

固定默认值必须能由声明的0至6位物理精度精确表示；超过精度或SQL函数/表达式在生成/规划前明确拒绝。MySQL默认以受控文本常量输出，结构反查保留该常量，尾零差异按同值归一；不放宽未知数据库表达式或精度缩窄门槛。

日内Excel文本保持原LocalTime简短秒位及3/6/9位小数组，原生TIME输出总小时。原详情picker和原列表普通文本筛选继续使用原模板，不增加控件、按钮或步骤。

## 接入与回退

更新Core、Data、Generation成套源码，通过原本地助手同步运行时及配置，再按元数据重新生成对应后端页面并严格构建。仅更新页面时，缺少时间依赖的旧目标必须被拦截。当前候选缺任一时间合同文件，即使同时删归属条目也拒绝；旧目标缺文件仍可正常预览完整升级。手写partial仍只首次创建。

原平台/示例模型没有业务time列，常规再生成不应因此改变现有产物。无需修改前端、数据库结构、旧数据或live元数据。新增TIME业务列或改变物理精度时仍走原“预览→执行→核验”流程，不启动自动DDL。回退须成套恢复生成器、运行时和受管产物；已有time业务不能退回不支持该类型的生成器继续生成。
