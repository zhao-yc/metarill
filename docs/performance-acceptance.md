# Java／C# 同条件性能测量

当前仅交付测量工具及本机合同回归，**尚未执行 Server-200 双端性能实验，V08 未通过**。工具不改变前后端、元数据、生成模板或接口，也不把业务测试耗时当作性能成绩。

## 实验前必须固定的条件

| 条件 | 可审查证据 | 当前状态 |
| --- | --- | --- |
| Java／C# 版本 | 两套独立生成应用的源码提交、元数据、手写扩展、构建命令和镜像摘要 | 尚未建立正式配对基线；不是拿现有在线 YZP 与新应用直接压测 |
| 数据与索引 | 同样规模／分布／固定ID、逻辑删除／项目范围、种子和索引快照，实验前后核对 | 尚未采集，不由HTTP响应散列替代 |
| 实际SQL | 各场景执行SQL／参数类型／查询次数及事务范围；分页COUNT、关系、锁和写入钩子不能缺省 | 尚未采集，不由方法名或SQL模板推断 |
| 计算及数据库资源 | 同一200主机、两个独占应用容器，明确相同CPU/内存/交换/CFS/CPU集合；共享MySQL版本、限制、缓冲和并发负载固定 | 工具能真实读取应用容器前后状态；本轮尚未执行Docker，MySQL仍须另核 |
| 接线与身份 | 证明URL属于对应容器，页权限／数据范围及账号角色相同 | 不能仅凭配置写了java/csharp就认为成立 |
| 业务与清理 | 原接口场景响应一致；写入仅限独占样本，保存失败／晚期回滚及清理记录 | 工具支持多步回放和失败留证；隔离样本租约及清理程序尚未准备 |

上述证据未全时，工具结果只是测量数据。`releaseAccepted` 始终为false，不自动签发首版性能验收，也不证明CPU/内存整体没有退化。计划仍需完成简单CRUD、带COUNT分页、权限/关系读取、复制/批量导入、文件及传播维护等代表性场景；JSON工具不测二进制下载吞吐，需另补该采集入口。必须保留同条件比较，不能换用微基准代替端到端要求。

## 配置与运行

Python标准库即可运行，无新增运行时依赖。将 `tools/performance/paired.example.json` 复制到 `.local/performance/<本轮>/settings.json` 后填写本轮实际配置。示例使用不可达回环端口、虚拟容器名和示例runId，只展示当前demo原接口的分页及CRUD形状，**不是已验证的Java配对基线，不能直接用于真实测试**。实际Java基线需同页面ID、协议与种子，不能为了工具通过修改原接口。

`headers` 使用每端自己的原 `loginStateId` 等认证头，只放私有配置；不把会话或响应正文写进报告。`baseUrl` 不接受用户密码、查询、片段或尾斜线。两端地址和容器必须不同；每轮使用新的32位runId及新的私有输出目录，失败不覆盖旧目录重跑。认证头、源配置、数据库及运行日志不能提交。

```powershell
# 完全离线：不建立HTTP/SSH连接，不运行Docker。
python tools/performance/paired_http.py validate --config .local/performance/<本轮>/settings.json

# 以下是真实业务/SSH操作，仅在已准备并核对独占实验范围后执行；本轮没有执行。
python tools/performance/paired_http.py run --config .local/performance/<本轮>/settings.json --ssh-host <已确认的200别名> --output .local/performance/<本轮>/measurement

# 本机合同回归：仅回环HTTP；SSH、Docker和MySQL均不执行。
python -m unittest discover -s tools/performance -p test_paired_http.py -v
```

每条Docker命令由SSH在远端先验证本机地址含192.168.31.200，再显式使用该机Unix socket，并清除DOCKER_HOST/DOCKER_CONTEXT影响；严格校验已有主机密钥，不自动信任新指纹。首次连接仍应按既有服务器接入规则确认指纹。只读精确容器的运行状态、镜像ID、CPU/内存限制及stats，不读容器环境或凭据，不执行本机Docker。

## 回放与统计合同

- `scenarios[].steps` 按原接口依次执行，支持GET/POST/PUT/PATCH/DELETE及JSON请求体。每步显式断言HTTP状态及业务字段，原R响应必须有数值 `/code=200`；HTTP200中的业务500不算成功。不跟随重定向，不重试业务请求；失败立即停止当前场景的后续步骤，其它已安排场景保留实际结果。
- `capture` 按严格JSON Pointer捕获标识，用 `${record}` 等传给后续步骤。保留字符串ID和null，不把省略/null混同，也不把True与1混同。路径变量百分号编码。保留变量为run、scenario、phase、concurrency、round、iteration，命名应覆盖这些维度以隔离预热、并发和轮次样本。
- 按完整解析后的JSON计算响应摘要，按相同迭代号逐步比较两端；只允许通过 `ignorePointers` 明确声明动态字段，缺失路径拒绝。示例只排除服务端新建ID；不能排除全部data掩盖查询少行、权限不同、关联错误或业务失败，正式忽略清单须随证据审查。只做类型保守比较，格式不同导致不一致时先核实协议，不自动放宽。
- 至少3轮、每轮至少100个场景。每个并发档位两端分别预热，次数为max(配置预热次数,并发数)，不计入正式成绩。正式轮次交替先Java/先C#，每端内部按固定并发线程回放同样次数的完整业务场景。当前客户端每请求独立HTTP连接，不测浏览器、长连接池或TLS连接复用；两端必须保持该条件。请求timeout是Python阻塞网络操作的socket期限，不声称覆盖DNS及整个场景的严格墙钟期限。
- 报告p50/p95/p99为最近秩百分位，单位ms；场景吞吐为成功场景数/本轮墙钟秒，**不是请求数/秒**。每步延迟另保留。真实失败数单列，失败不能作为低延迟成功样本；零时间/无样本不产生无限吞吐或通过结论。
- 每端正式测量期间采集对应容器stats，保留原始值和采样时刻、CPU百分比均值与观察到的内存最大值；离散采样最大值不等于进程真实峰值。每轮每端至少2份有效采样，过短或采样失败则测量无效，应重新评估独占样本/次数后建立新轮，不能伪造资源数据。实验前后容器ID/镜像及资源限制必须一致。
- 当前阈值由配置明确指定，示例p95比值上限1.10、吞吐比值下限0.95仅为提案。至少三分之二轮同时可比且超过任一阈值，标记稳定退化并阻断工具通过；任何业务不一致或资源证据不足也返回非零。未稳定但出现单轮退化仍保留逐轮数据，正式阈值、波动及首版判定需同批审查。

## 结果与失败处理

`intent.json` 先记录runId和配置摘要；`events.jsonl` 每次预热/正式意图/完成后追加并落盘，保存已完成阶段。`measurement.json` 保存完整汇总；异常另写不含异常正文的 `failure.json`。报告只保存响应摘要，不保存认证头、正文或口令。私有原始SQL/样本证明也应脱敏并另存。

写入正常场景应像示例一样以原接口删除结束，但软删墓碑仍是本轮数据；失败或中断可能留下活动样本或墓碑。工具不猜测失败写入是否提交，不扩展删除范围，不自动重试或批量硬删；必须由该轮独占夹具核对精确所有权后清理并独立核零。没有新的正式范围，不复用此前A15/C12等已结束租约。

## 本轮验证

2026-10-28：18项本机回归通过、零失败，含实际回环HTTP多线程创建/详情/删除、业务失败不续做、不重试、不跟随302、超大字符串ID/null、动态字段精确排除；其余覆盖交替顺序、预热分离、容器身份/资源限制、采样失败、零计时、指针/重复键/阈值。Docker及SSH均为内存桩，不能计作真实200采样。第一次资源失败反例发现Windows低分辨率monotonic可能零跨度，改用perf_counter并显式拒绝零吞吐后通过；原失败日志保留。

CLI失败/中断已完成阶段保留、凭据/异常正文不落报告、旧输出拒绝覆盖也有明确反例。配置示例另做离线validate；CI已接同一回归命令，远端结果以实际运行记录为准。本轮没有Server-200性能负载、数据库对象、容器创建/删除、前后端产品改动、跨端或性能成绩。V08只推进测量准备，首版总门槛保持未完成。
