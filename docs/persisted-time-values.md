# TIME写后值与回执一致

日期：2026-10-29；起始产品e3f7956，进度C37。修复来源是C36后续真实参数只读核验，不修改原页面或数据库结构。

## 证据与问题

同一已核实Server-200/MySQL8.4.11实例，直接MySqlConnector 2.6.1文本/预编译参数共24个只读向量，FreeSql实际参数化查询12个对照向量。两者结果一致，每个FreeSql查询确有一个参数，没有DDL/DML。程序集版本2.0.0.0是驱动稳定程序集身份，实际依赖包通过deps核实为2.6.1，不能将其误报为安装旧驱动。

当前SQL模式下，第七位小数秒不进入TIME(6)；TIME(0/1)还会按数据库规则舍入。例如12:34:56.9876549参数在TIME(6)返回12:34:56.987654，在TIME(0)返回12:34:57；日末23:59:59.9999999在低精度表达式可变成24:00:00。只读CAST不是持久化证据，但已证明直接返回请求内存值不能保证与数据库相同。

## 修复

生成器仅为包含真实物理time列的表生成写后回读。普通新增、更新、复制和复用这些入口的导入，在Mapper写入成功后、写后关系协调/观察器及VO回执前，通过同一DatabaseSession当前事务一次SELECT读取固定TIME列。主键始终是long参数，表/列来自已编译元数据并经适配器标识符校验；不展开整行，不开新连接，不改SQL模式或时区。

数据库提供程序承担实际SQL和驱动值转换，Service不判断数据库品牌。MySQL适配器要求唯一主键结果和完整列数，保留TimeSpan、合法总小时文本及null；缺行、多行、列数/类型/范围损坏或取消明确失败。其他提供程序未实现时拒绝，不能静默使用内存值。

回读值更新当前实体后才通知写后观察器并生成回执。若数据库精度后的值超出原时间控件日内范围，或回读失败，外层原事务回滚，不提交记录或通知观察器。不改变省略字段与null的区别；更新未发生写入时不增加回读。写前手写BeforeSave仍接收提交值，SQL精度后的规范值通过写后阶段提供，不宣称写前规则已经自动考虑物理精度。

## 性能与接入边界

每次含TIME的实际写入增加一次窄列查询，所有物理时间列一并读取，不逐字段往返。没有time的原平台/示例模型不生成此调用。新增数据库往返成本仍须同条件测量，不能据离线测试宣称性能持平。

成套更新Data、生成器及本地助手运行时后，正规再生成有TIME字段的后端；旧目标缺少新增适配partial时仍可预览完整运行时升级，当前候选不能同时删文件及归属绕过依赖门禁。手写partial仍只首次创建。原前端、元数据、物理结构和数据无需随本次修复修改，也不启动自动DDL。已有生成TIME应用不能只替换生成代码而遗漏新运行时。回退需成套恢复，并重新核对写后回执精度风险。
