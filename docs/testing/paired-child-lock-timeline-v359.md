# V359 同父导入的父锁与提交区间

2026-11-06，Server-200 独占轮次 `cf9d1a1910344b138ca20f3f6e4b5025`，沿用 V358 的 Java `e348fd6c` 和 C# `12e968a` 镜像，使用同一 MySQL 实例、共同关系索引、原普通账号、各 10,752 条同摘要种子及同一父记录。每端执行四个单请求及八组四并发，每组完成后发下一组。原 XLSX 用实际 SheetJS 解析。每个请求只改变八行的样本名，保留金额和备注。

由 JDBC 和 .NET 原命令观察器分别记录父锁调用开始、返回、同连接同事务的提交调用开始和返回。前一段含取锁等待、语句执行及驱动开销。中间一段是应用可确认已取得父锁的保守区间。提交段覆盖驱动提交调用，不能确定锁在该区间的何时释放。每组四个已确认持锁区间均无重叠。

| --- | --- | ---: | ---: |
| 单请求，各 4 个 | 首次父锁调用 | 2.8 | 0.8 |
| 单请求，各 4 个 | 父锁返回至提交开始 | 122.1 | 48.1 |

| 四并发，各 32 个 | 提交调用 | 46.7 | 53.5 |

四并发按实际取得父锁的先后排序。第一到第四位，Java 首次父锁调用的中位数分别为 4.8／138.7／275.6／406.0 ms，C# 为 2.1／109.4／198.4／306.3 ms。已持锁至提交前的区间中，直接被下游命令观察边界覆盖的中位数为 Java 48.4 ms、C# 15.5 ms。C# 合并命令观察到首个结果返回，随后消费的结果落在观察边界之间，不能把这部分直接算作应用处理开销。

72 个原请求均成功，两端各 288 行的父键、缓存名、金额、备注和活动状态逐值核对。逐请求匹配相同父键、事务及八条写入，C# 每请求均为七次插入与缓存合并。独立复算 130 份证据。新 SSH 核验双库、临时账号、18 个容器位置、网络、所有权记录、临时凭据及数据目录全部回收，私有审阅密钥备份摘要匹配。

本轮观察下，C# 在提交调用略长，但提交前持锁区间更短。该排序与 V358 持续回放的端到端结果不同。观察器增加参数摘要及采集成本，每组清空后再发也改变了到达节奏，无法用本轮区间推断正式回放的瓶颈。下一步在持续回放中采集同样的少量时间点，减少或关闭逐命令参数摘要和落盘，并用前后无观察对照核对采集影响。MySQL 首版性能继续以 [V358 正式复测](paired-child-insert-cache-timing-v358.md) 判定。
