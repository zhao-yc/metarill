## V452 表单条件模型

原模型使用 `status=1 AND segment=@formParameters.segment`。普通账号真实登录，从原菜单进入列表并打开详情。原列表候选请求没有表单数据，详情发送的表单存储没有分组标量。合计 3 次 `findNameIdChecked2204` 返回 HTTP 400，原错误弹窗会遮挡页面。此夹具未设置原自动回传和候选联动标志，暂不把结果归因于有效联动配置的 C# 兼容性回归。原 Java 非冗余候选也明确要求参数存在，详见 `NonRedundantReadService.appendCandidate`。

关闭已记录的错误提示后，原多选弹层返回甲、乙、丙三条合格候选，排除停用、其它分组和逻辑删除样本。已选甲正常显示，草稿增加乙后取消仍为甲，重新打开并确认后通过原表单成功保存。原列表及再次进入详情回显甲、乙。原登录、更新、注销各一次 HTTP 200，目标详情两次 HTTP 200。独立 MySQL 读回按顺序验证 `["9007199254745001","9007199254745002"]`，原复选、隐藏数组和对照行保持，名称没有物理缓存列。确认注销后活动会话为 0，已撤销会话为 1。整轮因动态复选未过保留为部分验收。

## V453 固定分组对照

第二轮只在合成元数据的复选字段 2204 将条件改为 `status=1 AND segment=1`，其余配置、C# 源码、前端模板、控件和权限沿用。该对照验证原控件在固定条件下的实际操作。

- 普通账号登录、原菜单、列表和详情均成功。复选候选只显示甲、乙、丙，原多选弹层取消时保留原值。
- 两个控件分别增加乙后一次保存，关闭再打开能看到两组实际选择。独立 MySQL 核对多选按甲、乙的确认顺序，复选按该次候选展示顺序乙、甲。四个数组项均为精确字符串 ID。脚本最初误用多选顺序检查复选，按原控件实际候选顺序重新核验通过。
- 原全选先选中三项，再次点击清空。第二次保存后重新打开，复选保持为空，多选仍显示甲、乙。独立 MySQL 确认复选物理值为 JSON 空数组，保留多选、隐藏数组及对照记录，来源两行，合格候选三行，三个名称列都没有建到物理表。
- 原登录和注销各一次、原修改两次、目标详情三次、复选候选四次，均为 HTTP 200。独立 MySQL 核对普通角色和会话撤销。
