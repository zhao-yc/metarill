# 冗余跨表来源到非冗余目标（B72）

2026-10-26，提交基线 `35560a5`。本批补固定普通 R1 来源到 R0 目标的物理名称、固定单值派生名称、R0／R1 混合层，以及同一独立 R0 表重复处于根和叶的角色。最终状态、源码摘要和回归结果以本文验收表及[进度表](project-progress.md)为准。

## 固定范围与生成边界

R1 来源继续保存各层真实 ID 和原 `prefix_name` 缓存；R0 目标的物理名称照常保留，派生名称仍只保存关联 ID、按固定路径读取，不增加物理名称列。原 CascadeTree 组件、页面、样式、交互、接口、字符串 ID 和省略／null 区别沿用；未改原前端、模板或平台元数据。

所有行为在生成器、发布计划和 Data 运行时实现，不补丁修改生成的 `.g.cs`。生成 Service 引入其 R0 读取助手需要的查询类型；普通不含派生绑定的注册输出仍沿原三参数入口，保护既有生成文件稳定。

## 完整计划与事务

物理目标名称仍交给 `RelationMutationPlan`，该入口继续拒绝逻辑名称。新增 `RelationMaintenanceCatalog.CompileWithDerivedCrossTables` 同时验证物理绑定、派生绑定、原维护整表计划和混合反向依赖；逻辑名称不会被静默忽略或冒充物理字段。

每条派生绑定必须具有原控制列／层 key、准确来源 ID／缓存、R0 单值字符串终点、同项目真实身份列和活动范围。虚拟、凭据、数组、歧义路径、坏同伴、跨项目及未知全局派生仍拒绝。完整维护不能形成来源缓存闭包时整个发布失败。物理与混合执行器的字段依赖额外合并判环，防止两边各自无环但共同构成循环。

真实终点改名、R0 中间关联 ID 切换及删除，在原 Service 事务内更新当前项目活动来源，继续触发依赖来源缓存的下游副本。反向队列复用原最多 128 行批次、当前锁读、写后核验及完整物理结构预检；不改关系 ID、业务和审计字段，不重入消费者页面写入口。目标尾部异常使目标、所有已写来源和下游一起回滚。

原 `RelationMaintenanceExecutor` 仍处理历史缓存，并向下游传播；第二次执行无变化返回 0。没有启动自动回填，也不把 R1 源数据自动转换成 R0。

## 升级与剩余范围

已有正确物理缓存列的 R1 来源不需要新增 DDL；R0 派生名称仍不建物理列。使用同版生成器和 Data／包内 Foundation，正规再生成来源、目标和下游服务及注册计划，保留手写 partial；不能只替换一个生成 Service。涉及缺失物理列时先走结构预览→明确执行→核验。历史错误缓存由原维护入口显式回填。

回退前保留原生成归属清单、手写文件和历史业务备份；按同版运行时和生成服务整体回退，不混用旧物理传播器与新逻辑定义。拒绝的定义不应通过手改注册代码绕过。

本批固定身份生成 HTTP 与完整源码包构建不等于 Production 正式用户／独立空库、浏览器、真机或性能验收。R1 来源自身重复参与 R0 层、共享辅助槽位、任意派生／多值终点、复杂父范围和未确认非空路径 Excel 继续保留原边界；B09／B10／B11 及整个 MySQL 首版仍未完成。不合 main、不部署生产。
