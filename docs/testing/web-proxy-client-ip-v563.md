# V563 Web 反向代理的客户端限流

2026-11-08，以 `1bd29bb4` 作为修复前产品对照。平台与完整业务应用的登录、登录失败保护和 Agent 入口使用 ASP.NET Core 的连接客户端地址。旧平台在同一 TCP 对端送达十次登录探针后，第二个转发地址同样收到限流响应。应用需要在认证和限流前恢复经过核实的客户端地址。 [ASP.NET Core 代理机制](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/proxy-load-balancer?view=aspnetcore-10.0)

平台和生成的完整应用使用同一接线。默认信任列表为空，显式配置的直接 TCP 对端才可提供 `X-Forwarded-For` 最后一项。缺少对端、配置为空或不匹配时，原连接地址继续生效。配置错误在 Web 启动时明确拒绝；不接受框架的全局任意代理开关。 [部署配置](../web-reverse-proxy.md)

| 验证 | 平台 Production | 生成的独立应用 Production |
| --- | --- | --- |
| 旧平台对照 | 第一个客户端耗尽额度后，第二个地址同样收到 HTTP 503 | 使用右侧默认配置复验其连接对端行为 |
| 修复版、配置受信对端 | 同一个地址第 11 次仍为 HTTP 503，第二个地址进入原表单验证，HTTP 200 | 同一个地址第 11 次仍为 HTTP 429，第二个地址进入原表单验证，HTTP 400 |
| 未配置 | 两个转发地址共享额度，均返回原限流状态 | 两个转发地址共享额度，均返回原限流状态 |
| 非受信对端 | 11 次轮换伪造地址仍共用同一额度，末次 HTTP 503 | 11 次轮换伪造地址仍共用同一额度，末次 HTTP 429 |
| 启动检查 | 无效代理地址和全局转发开关均失败 | 无效代理地址和全局转发开关均失败 |

探针通过本机 Kestrel 和实际 TCP 回环连接请求原登录路径，表单有意缺少登录字段。测试地址使用文档保留段。本轮验证真实宿主接线和原限流状态，不使用真实账号、Redis、MySQL 或外部网关。探针进程停止，临时设置删除。修复版平台和公开 Full 657 文件均严格发布。API 定向 18 项通过、零跳过，含最后一跳、错误格式、IPv4 映射、缺失对端、非受信对端、Host/Scheme 及原 URL 回归。

用旧提交重新生成同一元数据模型，再使用当前 CLI 的 sync-runtime 正式预览并应用。事务写入 3 份受管文件，删除 0 份。对照新旧候选的 389 份前端文件逐字一致，旧工程自有 AppID、私有设置及手写 Service 的摘要均保持。更新后独立宿主严格发布并重新运行原登录 TCP 探针，客户端分流与伪造拒绝通过。
