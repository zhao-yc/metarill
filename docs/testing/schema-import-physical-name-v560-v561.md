# V560／V561 反查导入使用 MySQL 实际表名

2026-11-08。使用 `0e64ed3a` 和本次补丁分别严格发布 Production 宿主。在 Server-200 固定镜像新初始化独占 MySQL `lower_case_table_names=1`，两端各使用独占平台库和业务库。该模式接受大小写别名，物理表名保存为小写。[MySQL 8.4 名称规则](https://dev.mysql.com/doc/refman/8.4/en/identifier-case-sensitivity.html)

| 验证 | 结果 |
| --- | --- |
| V560 修复前 | MySQL 目录返回 `mixed_source`。原接口用 `mixed_source` 与 `MiXeD_Source` 分别读取同一张表，草案表名与结构指纹随输入变化。混合名称审核及确认成功，独立 SQL 读到配置使用 `MiXeD_Source`。 |
| V560 修复后 | 获取表的元数据锁后，从 MySQL 列目录同一次查询获得实际表名及列数。两种拼写生成相同物理名和结构指纹。确认计划、回执与独立配置读回均使用 `mixed_source`，登记后用两种拼写重复审核均被拒绝。源结构与业务行逐项匹配。 |
| V561 敏感模式回归 | 同一修复宿主在 Server-200 原模式 0 的新独占双库中验证。两张仅大小写不同的真实表仍分别读取，同项目逻辑冲突在审核拒绝，共享库的不同项目可各自登记。 |
| 自动化回归 | 原离线事务夹具只返回单列计数，首次全量 10 项未通过。将夹具更新为数据库现在返回的表名与计数后，成功、取消与回滚合同继续通过。另用离线夹具覆盖 0／1／2 三种返回规则。最终数据层 1,597 项通过、32 项条件跳过，CLI 和导入计划定向 46 项通过、零跳过。 |

模式 1 的独占 MySQL 容器、四库、账号及只读材料绑定随容器精确回收。模式 0 的双库、账号及所有权独立核零。两轮 Redis、转发及私有材料均已核清。模式 2 只有离线覆盖，仍待对应平台实际 MySQL 验证。
