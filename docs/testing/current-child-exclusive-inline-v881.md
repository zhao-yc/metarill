# V881 排他父锁与单次缓存写入对照

2026-11-10。基线为 `ffcd80d36cc90283e7cb065ba78f65d1874d4c25`。隔离试验把已通过部署证明后取得父记录锁的那条 SQL 从 `FOR SHARE` 改为 `FOR UPDATE`，后七行仍使用同一事务证明完成单次缓存写入。固定镜像的 54 份载荷只替换 Data DLL 和 PDB。对比 3,057 个归一化方法体，只有这段取锁逻辑的异步状态机变化。严格编译和 Data 回归通过，1,602 项通过，32 项按环境条件跳过。

Server-200 上使用与 [V879 默认路径](current-child-log-volume-v879.md) 和 [V880 已配置共享锁](current-child-shared-log-volume-v880.md) 一致的 MySQL 8.4.11、持久化配置、存储设备、普通身份、共同索引与八行工作簿。三轮试验各自使用独占样本。V881 的 12 个窗口、1,200 个计时请求及 32 个预热均有效，两端各 4,928 条明细逐值读回一致。SQL 复核确认每笔使用排他父锁、八条 INSERT 和首行一条缓存 UPDATE。

排他单次和共享单次每百笔 binlog 均为 344,800 字节，较默认的 671,700 字节下降 48.7%。排他单次四并发的 redo 写入为 785,920–800,768 字节，提交均值为 73.39–80.43 ms，低于默认的 87.01–94.42 ms。尽管日志和提交耗时下降，排他单次的四并发三轮仍因吞吐低于 Java 的 95% 触线。单并发另有两轮触线。与相同单次写入的共享锁对照结合，当前固定样本的四并发瓶颈仍主要表现为排他父锁等待。
