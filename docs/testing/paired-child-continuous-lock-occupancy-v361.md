# V360／V361 同父导入的连续事务状态采样

2026-11-06，使用 Server-200 MySQL 8.4.11、Java 镜像 `e348fd6c`、C# 产品 `ef77e03` 和镜像 `12e968a`。两轮沿用 V358 的持续并发调度、共同索引、原普通账号、每端 10,752 条同摘要种子和原八行工作簿。应用内 SQL 观察关闭。另有一条只读连接，在数据库侧按当前合成账号和库聚合。保存阶段计数，事务标识和 SQL 正文均不导出。

V360 使用 75 ms 间隔。802 个样本中，有四个完整四并发时段未匹配到任何 InnoDB 事务状态，阶段估计作废。MySQL 8.4.11 源码显示，事务缓存只有在距上次读取超过 100 ms 时才允许刷新，因此 75 ms 的连续查询可能让阶段分类长期依赖旧快照。V360 的 HTTP 和物理校验仍成立，四并发吞吐比为 85.2%／78.0%／90.5%。 [MySQL 8.4.11 事务快照刷新实现](https://github.com/mysql/mysql-server/blob/mysql-8.4.11/storage/innobase/trx/trx0i_s.cc#L627-L645)

V361 轮次 `b83186481e27477bbc20e5273d616c27` 改用 147／163／181 ms 错开间隔。共 360 个样本，六个四并发时段中，每段最低时间覆盖为 100.0%，事务集合变化率最低 96.9%，匹配到事务状态的比例最低 96.2%。独立复算的最短实际采样间隔为 149.0 ms，六组探针查询 p95 最高 4.1 ms。

C# 相对 Java 的全部等锁占用差为 +19.9／+54.0／+73.2 ms／请求，已写占用差为 +14.4／+19.2／+7.1 ms／请求，显式提交占用差为 -8.0／+2.5／+16.4 ms／请求。已写状态只是持锁区间的代理，可能漏掉首次写入前的持锁时间，也无法标定提交中实际释放的时点。PROCESSLIST 和 InnoDB 事务状态的采集边界不同，父查询分类无法解释未识别的等锁。各状态是按时间权重估算的聚合值，不能反推出单个请求的精确时长。

三轮中，数据库连接有活动命令时的已写占用均增加，连接空闲时的已写占用变化方向不一致。结合 V357 中首行之后仍逐行发送父候选重验和合并写入，下一项对照应测量能否把这两条命令合成一次往返，同时保留父失效、候选拒绝和末行整批回滚的原协议。

两轮均通过 32 次预热和 1,200 次正式请求的回包核对，每端 4,928 条新增明细逐值一致。各有 59 份端到端与物理证据独立复算，双库、账号、16 个容器位置、独占网络、所有权、临时凭据和数据目录均由新 SSH 独立核清。
